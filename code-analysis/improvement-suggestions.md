## 2. 改进建议清单（按优先级排序）

### 2.1 P0 - 紧急修复（影响系统稳定性）

#### P0-001: Worker 心跳机制重构

**来源**: 逻辑缺陷 #001  
**模块**: Worker System  
**文件**: `worker/handlers/build_handler.py`  
**问题**: Worker 处理长时间任务时，心跳线程可能在任务完成前被意外停止，导致消息可见性超时，任务被重复执行。  
**影响**: Agent 构建任务重复执行、浪费计算资源、产生重复项目文件  
**建议方案**:
1. 重构心跳线程管理，使用守护线程 + 事件信号机制
2. 添加任务幂等性检查（基于任务ID的去重机制）
3. 在任务开始时记录执行标记，防止并发执行
4. 增加心跳间隔的动态调整能力

**预计工作量**: 2天  
**风险等级**: 低（改动范围可控）

---

#### P0-002: API 流式响应错误处理完善

**来源**: 逻辑缺陷 #002  
**模块**: API System  
**文件**: `api/v2/services/agent_runtime_service.py`  
**问题**: 流式响应中缺少完整的错误处理，当 AgentCore 调用失败时，客户端可能无限等待。  
**影响**: 客户端挂起、资源泄漏（未关闭的连接）、用户体验差  
**建议方案**:
1. 添加流式响应超时机制（可配置超时时间）
2. 在 stream 中断时发送标准错误事件（SSE error event）
3. 确保异常情况下资源正确清理（使用 `async with` 或 `try-finally`）
4. 添加客户端心跳检测，及时发现断开的连接

**预计工作量**: 1天  
**风险等级**: 低

### 2.2 P1 - 高优先级修复（影响核心功能）

#### P1-001: 会话并发控制

**来源**: 逻辑缺陷 #003  
**模块**: API System  
**文件**: `api/v2/services/session_service.py`  
**问题**: 会话管理缺少并发控制，多个请求可能同时修改同一会话。  
**建议方案**:
1. 使用 DynamoDB 条件更新（ConditionExpression）
2. 添加乐观锁机制（版本号字段）
3. 实现会话级别的互斥锁

**预计工作量**: 2天

---

#### P1-002: 断点恢复逻辑加固

**来源**: 逻辑缺陷 #004  
**模块**: Worker System  
**文件**: `worker/handlers/build_handler.py`  
**问题**: 断点恢复逻辑在阶段状态不一致时可能失败。  
**建议方案**:
1. 添加状态一致性检查（恢复前验证所有前置阶段状态）
2. 实现更健壮的恢复逻辑（支持从最近的一致状态恢复）
3. 记录详细的恢复日志

**预计工作量**: 3天

---

#### P1-003: Agent Factory 循环依赖检测

**来源**: 逻辑缺陷 #005  
**模块**: Agent Factory  
**文件**: `nexus_utils/agent_factory.py`  
**问题**: 工具依赖解析时循环依赖检测不完整，可能导致无限递归。  
**建议方案**:
1. 实现基于图的循环依赖检测算法（DFS + 访问标记）
2. 添加递归深度限制（默认最大深度 10）
3. 提供清晰的错误信息，指出循环依赖链

**预计工作量**: 2天

### 2.3 P2 - 中优先级改进（提升代码质量）

#### P2-001: 接口规范统一

**来源**: 接口冲突分析  
**问题**: 143个接口冲突，包括参数不一致和返回类型不一致。  
**重点修复对象**:

**参数不一致（高严重度，需优先统一）**:

| 函数名 | 冲突位置数 | 建议标准 |
|--------|-----------|---------|
| `get_workflow_config` | 3处 | 统一为 `get_workflow_config(workflow_type: str)` |
| `get_workflow_stages` | 2处 | 统一为 `get_workflow_stages(workflow_type: str)` |
| `get_agent` | 5处 | 按层级区分：DB层用 `agent_id`，业务层用 `agent_id`，模板层用 `agent_name` |
| `get_stage` | 3处 | 统一为 `get_stage(project_id: str, stage_name: str)` |
| `normalize_stage_name` | 2处 | 统一为 `normalize_stage_name(stage_name: str, workflow_type: str = None)` |
| `list_agents` | 3处 | 按层级区分，保持各层参数合理性 |
| `list_projects` | 3处 | 按层级区分，保持各层参数合理性 |
| `create_project` | 3处 | DB层用 `project_data`，服务层用 `request` |
| `delete_project` | 3处 | 统一为 `delete_project(project_id: str, delete_local_files: bool = True)` |
| `run_workflow` | 2处 | 区分引擎层和入口层接口 |
| `execute_stage` | 2处 | 统一为 `execute_stage(context, stage_name, input_message, state)` |
| `deploy_to_agentcore` | 2处 | 统一参数命名和类型 |
| `project_init` | 2处 | CLI层和工具层保持各自合理接口 |

**返回类型不一致（中严重度）**:

| 函数名 | 问题 | 建议 |
|--------|------|------|
| `mark_stage_running` | `bool` vs `None` | 统一返回 `bool` |
| `mark_stage_completed` | `bool` vs `None` | 统一返回 `bool` |
| `mark_stage_failed` | `bool` vs `None` | 统一返回 `bool` |
| `delete_session` | `bool` vs `Dict` | DB层返回 `bool`，服务层返回 `Dict` |
| `get_session` | 类型不一致 | 统一返回 `Optional[Dict[str, Any]]` |

**建议方案**:
1. 制定接口设计规范文档
2. 为所有公共函数添加完整的类型注解
3. 使用 `mypy` 进行静态类型检查
4. 在 CI/CD 中集成类型检查

**预计工作量**: 5天

#### P2-002: 未使用导入清理

**来源**: 废弃代码分析  
**问题**: 618个未使用的导入分布在整个项目中。  
**重点清理模块**:

| 模块 | 未使用导入数 | 清理优先级 |
|------|-------------|-----------|
| `tools/generated_tools/` | ~200个 | 中（生成代码，需谨慎） |
| `api/v2/` | ~100个 | 高（核心API代码） |
| `nexus_utils/` | ~120个 | 高（核心工具库） |
| `agents/` | ~80个 | 中 |
| `worker/` | ~20个 | 高 |

**建议方案**:
1. 使用 `autoflake` 工具自动清理未使用导入
2. 配置 `ruff` 或 `flake8` 的 `F401` 规则
3. 在 CI/CD 中添加未使用导入检查
4. 对 `__init__.py` 中的导入需特别注意（可能是公共API导出）

**执行命令示例**:
```bash
# 使用 autoflake 自动清理
autoflake --in-place --remove-all-unused-imports --recursive .

# 使用 ruff 检查
ruff check --select F401 .
```

**预计工作量**: 2天（自动化工具 + 人工审查）

#### P2-003: MCP 模块整合

**来源**: 冗余分析  
**问题**: MCP 相关代码存在新旧两套实现（`nexus_utils/mcp_manager.py` 和 `nexus_utils/mcp/`），导致维护困难。  
**涉及重复**:
- `MCPServerConfig`: 2个定义
- `MCPClientFactory`: 2个定义
- `MCPManager`: 2个定义（旧版9个方法 vs 新版19个方法）

**建议方案**:
1. 将 `nexus_utils/mcp_manager.py` 标记为废弃（添加 `@deprecated` 装饰器）
2. 将所有引用迁移到 `nexus_utils/mcp/` 模块
3. 在 `mcp_manager.py` 中保留兼容性包装器（过渡期）
4. 设定废弃时间线（建议2个月后移除旧模块）

**预计工作量**: 3天

#### P2-004: 生成代码去重

**来源**: 冗余分析  
**问题**: `agents/generated_agents/` 和 `agents/template_agents/` 之间存在大量重复代码。  
**重复实例**:
- `StockAnalysisSystem` 类完全重复（`template_agents/` vs `generated_agents/`）
- `html2pptx` 相关函数完全重复（4个函数）
- AWS 网络分析工具的资源收集函数重复（`aws_resource_collector.py` vs `_part1/2/3.py`，15+个函数）

**建议方案**:
1. 建立生成代码与模板代码的关联机制
2. 生成代码应引用模板代码而非复制
3. 对 `aws_network_architecture_analyzer` 进行重构，消除 `_part1/2/3` 文件中的重复
4. 改进代码生成流程，避免产生冗余代码

**预计工作量**: 4天

#### P2-005: 错误处理框架统一

**来源**: 逻辑缺陷 #008, 冗余分析  
**问题**: 
- 错误处理不一致（`ValidationError` 有3个不同定义）
- MCP 客户端创建失败时错误信息不够详细
- 各模块错误处理模式不统一

**建议方案**:
1. 创建统一的异常层次结构：
   ```
   NexusBaseError
   ├── NexusValidationError
   ├── NexusConfigurationError
   ├── NexusConnectionError
   ├── NexusResourceError
   └── NexusWorkflowError
   ```
2. 统一错误响应格式（包含 error_code、message、details、suggestion）
3. 添加结构化错误日志
4. 为所有外部调用添加详细的错误上下文

**预计工作量**: 4天

---

#### P2-006: 资源管理改进

**来源**: 逻辑缺陷 #009, #011, #012, #013  
**问题**: 多处资源管理不完善，包括临时文件未清理、项目删除不彻底、S3上传重复、MCP连接泄漏。  
**建议方案**:
1. **临时文件管理**: 使用 `tempfile.TemporaryDirectory` 上下文管理器
2. **级联删除**: 项目删除时实现完整的资源清理链（S3文件 → 会话 → 阶段数据 → 项目记录）
3. **S3上传幂等性**: 使用内容哈希作为文件标识符，避免重复上传
4. **MCP连接池**: 实现连接池管理，配置重载时优雅关闭旧连接

**预计工作量**: 5天

## 5. 风险与缓解措施

### 5.1 实施风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 重构引入新 Bug | 高 | 中 | 充分测试，分步骤提交，代码审查 |
| 接口变更影响下游 | 高 | 中 | 保留兼容层，渐进式迁移 |
| 工时估算不准确 | 中 | 高 | 预留 20% 缓冲时间 |
| 团队资源不足 | 中 | 中 | 按优先级分批实施 |
| 生成代码重构困难 | 中 | 中 | 改进生成流程而非逐个修复 |

### 5.2 缓解策略

1. **分支策略**: 每个改进任务使用独立分支，通过 PR 合并
2. **渐进式迁移**: 旧接口保留兼容层，设定废弃时间线
3. **回归测试**: 每次重构后运行完整测试套件
4. **代码审查**: 所有改动必须经过至少一人审查
5. **监控告警**: 部署后密切监控系统指标

## 6. 持续改进建议

### 6.1 开发规范

1. **编码规范**: 制定并执行统一的编码规范（使用 `ruff` 自动检查）
2. **接口设计**: 新接口必须遵循统一的设计规范
3. **错误处理**: 所有外部调用必须有错误处理
4. **资源管理**: 使用上下文管理器管理资源
